# Сверка с драйвером ядра Linux

Механизм уже реверснут и давно в майнлайне: `drivers/platform/x86/msi-wmi.c`.
Копия исходника — `msi-wmi.c` рядом с этим файлом (366 строк).

GUID совпадает дословно:

```c
#define MSIWMI_WIND_EVENT_GUID "5B3CC38A-40D9-7245-8AE6-1145B751BE3F"
```

Это наш `MSI_Event`. Коды в ядре — младший байт нашего `0x2200NN`.

## Расшифровка кодов

| Наш | Ядро | Обработка в ядре |
|---|---|---|
| `0x220029` | `CLAW_KEY_CENTER = 0x29` | `KE_KEY` → `KEY_F15`; комментарий: «MSI M-Center main menu» |
| `0x220021` | `CLAW_KEY_VOLUMEDOWN = 0x21` | `KE_IGNORE` |
| `0x220032` | `CLAW_KEY_VOLUMEUP = 0x32` | `KE_IGNORE` |
| `0x220062` | `0x62` | `KE_IGNORE`, «unknown WMI events found on MSI Wind» |
| `0x220063` | `0x63` | то же |

Пара `0x62`/`0x63` — **яркость экрана вверх и вниз**. В ядре они числятся
неизвестными («unknown WMI events found on MSI Wind»), так что здесь мы знаем
больше: определены нажатием 2026-10-02, пять нажатий вверх дали `0x220062`,
семь нажатий вниз — `0x220063`, в том же порядке. Обрабатывать их не нужно по
той же причине, по которой ядро игнорирует громкость: прошивка меняет яркость
сама, и действие на событие удвоило бы нажатие.
| `0x220004` | — | **в таблице отсутствует**, ядро про Cooler Boost не знает |
| `0x22006F` | — | **отсутствует**; у нас это P1 (Fn+F4), определено нажатием |

Ядро игнорирует громкость с пометкой
«These keys work without WMI. Ignore them to avoid double keycodes» —
это независимое подтверждение нашего наблюдения, что громкость обрабатывает
сама Windows через штатный HID. Для яркости комментария в ядре нет; наблюдение
здесь только в том, что яркость меняется и без нашего обработчика, то есть
действие на событие было бы вторым изменением поверх первого.

Прочие коды из ядра, которых мы пока не видели: `0x08` тачпад,
`0x56` Bluetooth, `0x57` камера, `0x5f` Wi-Fi, `0x60` turbo, `0x69` ECO,
`0x2a` и `0x58` — долгое и короткое нажатие M-Center quick access.
Диапазон `0xD0..0xD4` — generic MSI яркость/громкость/mute, на Wind не встречается.

## Чего в ядре нет, а у нас есть

Драйвер ядра работает с `MSIWMI_BIOS_GUID` (`551A1F84-FBDD-4125-91DB-3EA8F44F1D45`)
через `wmi_query_block` / `wmi_set_block`. **На GL72 такого класса нет.**

Вместо него машина отдаёт более поздний интерфейс MSI:

| Класс | GUID |
|---|---|
| `MSI_Software` | `{24418D6A-0A79-524C-9AB1-18B78CA68CE7}` |
| `MSI_Device` | `{4AFBD56B-9F91-8f49-81F5-995BA73822AF}` |
| `MSI_AP` | `{A1753D7C-B621-de4a-B41A-55716A0ECE7A}` |
| `MSI_System` | `{A1753D7B-B621-de4a-B41A-55716A0ECE7A}` |
| `MSI_CPU` | `{BD2A216F-2FB9-a640-B807-DDDBAD656891}` |
| `MSI_VGA` | `{1EC3EC7A-1E9B-e74a-9026-CF122B0BBD21}` |
| `MSI_Power` | `{2D3CBA6C-1C9C-7f41-B54C-F5D5D580D482}` |
| `MSI_Master_Battery` | `{40BA026D-075D-cd4a-9710-F7C57347CAC9}` |
| `MSI_Slave_Battery` | `{8DBCCF6E-9DB4-0e46-A3F2-99AFAAA77A7A}` |

Так что для нашей задачи msi-wmi.c полезен как расшифровка кодов, но не как
описание интерфейса — у GL72 он другой и шире.

## Гипотеза о передаче кнопок

Имя `MSI_Software` подходит под «сообщить контроллеру, что софт MSI запущен».
Похоже, именно это делает `MSIService.exe`, и именно поэтому без службы
события не приходят.

Опыт для проверки: прочитать экземпляры `MSI_Software`, `MSI_AP`, `MSI_Device`
при работающей службе, затем при остановленной, и сравнить значения.
Отличающийся бит и будет искомым флагом. Если он пишется — служба MSI
становится не нужна, и обработчик получится полностью самостоятельным.

## Поправки от 2026-10-02

**Гипотеза опровергнута.** Служба MSI кнопки софту не передаёт —
события приходят и без неё, см. [FINDINGS.md](FINDINGS.md). Соответственно
догадка, что `MSI_Software` сообщает контроллеру о запущенном софте MSI, неверна
дважды: класс описан как Class to ECRam Query/Set Software и содержит
**версию прошивки EC** (`1796EMS1.104`, 2016-02-23) по одному ASCII-байту
на экземпляр.

**Сама служба устроена как наш обработчик.** `MSIService.exe` импортирует
`MSIWmiAcpi.dll` — обёртку 2011 года вокруг класса `CMSIWmiAcpi` с методами
`QueryWMIProperty`, `SetWMIProperty`, `MethodWMI`, `MSIWMIEvent`, `AddHWND`
и `MSI_CallNamePipe`. То есть служба подписывается на те же WMI-события и
передаёт их `SCM.exe` по именованному каналу. HID не используется нигде.

**Коды, которых в ядре нет, а у нас они опознаны нажатием:**

| Код | Клавиша |
|---|---|
| `0x22006F` | P1 (Fn+F4) |
| `0x220279` / `0x220079` | ECO (Fn+F5) |
| `0x220062` / `0x220063` | яркость вверх / вниз (в ядре `KE_IGNORE`, «unknown») |

Не опознан пока только `0x220023`.

И поправка к модели кодирования: схема «префикс 0x2200 плюс скан-код ядра»
описывает не все коды. Три клавиши дают по паре кодов, различающихся ровно
битом 1 среднего байта: `0x220208`/`0x220008` тачпад, `0x220279`/`0x220079` ECO,
`0x224B57`/`0x224957` камера. Младший байт по-прежнему совпадает с таблицей ядра
там, где код в ней есть.

## Второй драйвер ядра: msi-laptop.c

`msi-wmi.c` описывает только hotkey-события. Про EC-флаги управления кнопками
говорит другой драйвер — `drivers/platform/x86/msi-laptop.c`:

```c
/* For set SCM load flag to disable BIOS fn key */
#define MSI_STANDARD_EC_SCM_LOAD_ADDRESS   0x2d
#define MSI_STANDARD_EC_SCM_LOAD_MASK      (1 << 0)

/* msi_scm_disable_hw_fn_handling() */
ec_read (MSI_STANDARD_EC_SCM_LOAD_ADDRESS, &data);
ec_write(MSI_STANDARD_EC_SCM_LOAD_ADDRESS, data | MSI_STANDARD_EC_SCM_LOAD_MASK);
```

Это тот же механизм по смыслу, что найденный у нас флаг `MSI_Software[0]`:
сообщить контроллеру, что кнопками займётся ОС. Отличие в пути — ядро пишет
прямо в порты EC через свой ACPI-драйвер, а из пользовательского режима Windows
тот же результат достигается записью в окно `MSI_Software` через WMI, без
ring-0.

Прочие адреса оттуда, полезные как карта (проверять на этой машине не пробовали,
окна `MSI_*` покрывают лишь часть адресного пространства EC):

| Адрес | Что |
|---|---|
| `0x2d` бит 0 | SCM load — обработку кнопок берёт ОС |
| `0x2e` биты 0,1,3,4 | Bluetooth, камера, WLAN, 3G |
| `0x2f` | какие устройства присутствуют |
| `0x33` бит 0 | автоматическое управление вентилятором; ноль — максимум |
| `0xe4` биты 1,3,4 | Turbo, ECO, тачпад |

Наш `MSI_Device` отдаёт всего 4 байта, поэтому прямого соответствия этим
адресам у него нет.

## Что ядро говорит о полях EC

Проверено два источника помимо `msi-wmi.c`.

### msi-ec (внедревесный модуль, BeardOverflow/msi-ec)

Хранит карты регистров EC по моделям. **Конфигурации для GL72, GL62 и платы 1796
в нём нет** — описаны более новые машины. Но сама карта полей отвечает на вопрос,
который мы оставили открытым:

| Поле | Адрес EC | Бит / маска |
|---|---|---|
| `cooler_boost` | `0x98` | бит 7 |
| `cpu.rt_temp` / `cpu.rt_fan_speed` | `0x68` / `0x71` | — |
| `gpu.rt_temp` / `gpu.rt_fan_speed` | `0x80` / `0x89` | — |
| `shift_mode` | `0xd2` | turbo `0xc4`, eco `0xc2`, comfort `0xc1` |
| `fan_mode` | `0xd4` | auto `0x0d`, silent `0x1d`, advanced `0x8d` |
| `charge_control` | `0xd7` | — |
| `webcam` | `0x2e` / блок `0x2f` | бит 1 |
| `fn_win_swap` | `0xe8` | бит 4, инвертирован |
| `super_battery` | `0xeb` | маска `0x0f` |
| `leds` micmute / mute | `0x2c` / `0x2d` | бит 1 |
| подсветка клавиатуры | `0x2c` / `0xd3` | база состояния `0x80` |

**Главное отсюда: статус Cooler Boost в контроллере есть** — `0x98`, бит 7.
Мы его не нашли не потому, что его нет, а потому что окна `MSI_*` этого адреса
не покрывают: все наши 123 байта лежат в других местах. Прочитать его можно
только прямым доступом к портам EC, то есть ring-0 драйвером.

### Документация майнлайна: Documentation/wmi/devices/msi-wmi-platform.rst

Описывает **методы** WMI-интерфейса MSI, а не свойства:

- `Get_EC()` — «флаговый байт и 28-байтовая строка версии прошивки контроллера»;
  младшие 4 бита флага — минорная версия, следующие 2 — мажорная.
- `Get_Fan()` — до четырёх 16-битных показаний в big-endian, `RPM = 480000 / значение`.
- `Get_WMI()` — версия интерфейса двумя байтами.

Байтовых значений для блоков `AP`, `Device`, `Software`, `System`, `CPU`, `VGA`
документ не описывает и прямо отсылает к msi-ec.

**Чем это полезно нам.** `Get_EC()` подтверждает нашу расшифровку `MSI_Software`:
байты `[6…33]` — это ровно 28 байт, и читаются они как строка версии прошивки.
Расшифровку мы получили чтением байтов как ASCII, а документация ядра называет
точно такую же структуру независимо.

**Чего это не даёт.** На этой машине документированных методов нет: проверены все
1605 классов в `root\WMI`, `Get_EC`, `Get_Fan` и `Get_WMI` не нашлось ни у одного,
а у всех классов `MSI_*` методов нет вовсе. Настоящие обороты вентилятора по
формуле `480000 / значение` прочитать нельзя — только наш однобайтовый тахометр
`MSI_AP[2]`, единица измерения которого остаётся неизвестной.

### Почему карты ядра не переносятся на наши окна напрямую

Ядро описывает **адреса** в EC, а интерфейс MSI на этой машине отдаёт **окна**
свойств, соответствие которых адресам неизвестно. Структурное сходство при этом
заметное и наши подписи подтверждает: у msi-ec в блоке CPU одно «живое»
показание температуры и отдельно кривая, и у нас в `MSI_CPU` то же — `[1]`
температура, `[5…10]` точки, `[12…17]` обороты. Но это сходство формы, а не
соответствие адресов, и выводить одно из другого нельзя.
