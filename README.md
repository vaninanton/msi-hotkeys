# msi-hotkeys

Свой обработчик аппаратных кнопок ноутбука MSI — замена штатного SCM целиком,
без ring-0 драйверов и без софта MSI вообще.

Работает и ни в чём от софта MSI не зависит: сам забирает кнопки у прошивки,
ловит их все, живёт в области уведомлений, показывает показания датчиков
и запускает произвольную команду по нажатию. Не сделано: автозапуск.

> **Только для платы MS-1796.** Карта байтов EC снята с ACPI-таблиц одной
> машины. На другой модели MSI те же окна ведут к другим адресам, а программа
> в один из них пишет, поэтому на незнакомой плате она отказывается запускаться.
> Ключ `--force` есть, но он для тех, кто сверил свой DSDT сам.
> Гарантий никаких — см. [LICENSE](LICENSE).

## Железо и система

| | |
|---|---|
| Ноутбук | MSI GL72 6QD, матплата **MS-1796** rev 1.0 |
| BIOS | `E1796IMS.10C` от 2018-01-17 (обновлений не будет) |
| Прошивка EC | `1796EMS1.104` от 2016-02-23 |
| CPU | i5-6300HQ (Skylake-H, 4C/4T), распаян, FCBGA1440 |
| ОС | Windows 10 Pro for Workstations 19045 |

Гейт проверяет `Win32_BaseBoard.Product`, а не маркетинговое имя: ACPI-таблицы
принадлежат плате, и MSI продаёт одну плату под несколькими названиями.

## Почему нужны права администратора

Классы ACPI-WMI не читаются без них: первое же чтение отвечает
`WBEM_E_ACCESS_DENIED` (`0x80041003`). Подключение к пространству имён при этом
проходит и без прав — отказ приходит позже, поэтому программа проверяет доступ
именно чтением байта, а не успехом подключения.

В релизный exe встроен манифест с `requireAdministrator`, так что Windows
спрашивает один раз при запуске. В отладочной сборке манифеста нет намеренно:
иначе `cargo test` не смог бы запустить тестовый бинарь (ошибка 740) —
подробности в [build.rs](build.rs).

Осторожно с проверками доступа: он выглядит непостоянным. Дважды за одну ночь
неповышенная сессия читала и даже писала успешно, а затем отказ возвращался.
Правдоподобное объяснение — хост провайдера `WmiPrvSE` поднимается по запросу
и выгружается примерно через минуту простоя: пока его подняла повышенная сессия,
он обслуживает и неповышенные обращения. Подробности в
[docs/FINDINGS.md](docs/FINDINGS.md).

## Как это работает

Кнопки сообщают о нажатии через **ACPI-WMI**, а не через приватный драйвер.

```
Пространство имён : root\WMI
Класс             : MSI_Event
Свойство          : MSIEvt : UInt32
GUID              : {5B3CC38A-40D9-7245-8AE6-1145B751BE3F}
Экземпляр         : ACPI\PNP0C14\0_0
```

### Кнопки надо забрать у прошивки, и это запись одного байта

```
класс     : MSI_Software
экземпляр : ACPI\PNP0C14\0_0
свойство  : Software : UInt8   (write=True)
значение  : 1
```

Это флаг «софт управления присутствует» — EC `0x2D` бит 0, тот самый, который
в драйвере `msi-laptop` ядра Linux называется `MSI_STANDARD_EC_SCM_LOAD`
с комментарием «set SCM load flag to disable BIOS fn key». Пока он 0, кнопки
обрабатывает прошивка и ACPI-событий не посылает — подписка при этом создаётся
без ошибки и молчит, на чём в этом проекте потеряли больше всего времени.
Как только он 1, кнопки уходят в `MSI_Event`. Ровно это и делает служба MSI
при старте, и ничего больше.

Программа пишет флаг сама и снимает его при выходе, возвращая кнопки прошивке.
Флаг остаётся установленным после аварийного завершения процесса; холодный старт
сбрасывает его в любом случае.

Проверено 2026-10-02: загрузка, в которой служба `Micro Star SCM` стояла
в `Disabled` и не работала ни секунды, затем наша запись — и все кнопки пошли.
Хронология опытов и опровергнутых версий в [docs/FINDINGS.md](docs/FINDINGS.md).

```
     MSI_Software[0] = 1          кнопки переходят к программе
             |
     MSI_Event в root\WMI
             |
      обработчик (admin)   ->   действие из actions.txt
```

Для сравнения, как это устроено у MSI: `MSIService.exe` — такой же подписчик
WMI-событий (через `MSIWmiAcpi.dll`), передающий их `SCM.exe` по именованному
каналу. Особого доступа к железу в этой схеме нет.

## Карта кодов кнопок

| Код | Кнопка | Откуда известно |
|---|---|---|
| `0x220004` | Cooler Boost | нажатие |
| `0x220029` | кнопка рядом с питанием, ранее Dragon Gaming Center | нажатие |
| `0x220021` / `0x220032` | громкость вниз / вверх | нажатие |
| `0x220062` / `0x220063` | яркость экрана вверх / вниз | нажатие |
| `0x220208` / `0x220008` | тачпад (Fn+F3) | нажатие; низкий байт `0x08` совпал с `msi-wmi.c` |
| `0x224957` / `0x224B57` | камера (Fn+F6) | `msi-wmi.c`, низкий байт `0x57` |
| `0x22006F`, `0x220023`, `0x220079`, `0x220279` | — | не определены |

Важно: **схема «все коды вида 0x2200NN» неверна**, и средний байт — не индекс
устройства. Тачпад и камера дают по паре кодов, и в обеих парах два кода
различаются ровно битом 1 среднего байта: `0x220208`/`0x220008`
и `0x224B57`/`0x224957`. То есть байт несёт что-то изменчивое. Простой чётностью
«включено/выключено» это не объясняется: девять нажатий Fn+F3 подряд дали один
и тот же код, хотя тачпад должен был переключаться каждый раз. Разбор и способ
проверки — в [docs/FINDINGS.md](docs/FINDINGS.md).

Состояния тачпада в читаемых байтах нет: за десять нажатий ни один из 107 не
изменился в такт, `MSI_Device` не дрогнул вовсе.

Громкость и яркость программа не обрабатывает намеренно: прошивка и Windows
успевают сделать своё до прихода события, и действие здесь удвоило бы нажатие.
Драйвер в ядре Linux игнорирует их по той же причине.

## Что опознано в EC RAM

Классы `MSI_*` — окна в EC RAM, по байту на экземпляр (у батарей — по слову),
с правом записи у `AP`, `Device` и `Software`. Всего читается 107 значений.

Карта снята с собственного DSDT машины, а не угадана по наблюдениям: `_WDG`
сопоставляет блоку идентификатор, метод прошивки `WQ<id>` перечисляет поля EC,
которые блок отдаёт, а `OperationRegion EC__` объявляет эти поля по именам.
Инструменты в [tools/acpi](tools/acpi), полная карта в
[docs/EC-MAP.md](docs/EC-MAP.md).

| Окно | EC | Что это |
|---|---|---|
| `MSI_Software[0]` | `0x2D`.0 | флаг «софт присутствует» — передача кнопок |
| `MSI_Software[6..33]` | — | версия прошивки EC и дата сборки, ASCII |
| `MSI_CPU[0]` | `0x33`.0 | 0 — вентилятор на максимуме, 1 — по кривой |
| `MSI_CPU[1]` | `0x68` | температура CPU |
| `MSI_VGA[1]` | `0x80` | температура GPU (0, когда карта спит) |
| `MSI_AP[2]` | `0xCD`? | вентилятор: единицы неизвестны, 77 в покое, 137–138 на максимуме |
| `MSI_System[0]` | `0xE4`.1 | Turbo |
| `MSI_Device[0]` / `[1]` | `0x2E` / `0x2F` | состояние и наличие Bluetooth, камеры, WLAN, 3G |
| `MSI_CPU[5..10]` / `[12..17]` | — | кривая вентилятора CPU: точки и значения |
| `MSI_VGA[5..10]` / `[12..17]` | — | то же для GPU |
| `MSI_Master_Battery[0]` | `0x31` | флаги: установлена, заряжается, разряжается, заряжена |
| `MSI_Master_Battery[6..11]` | `0x38`+ | процент, ёмкости, ток (со знаком), напряжение, температура |

Адреса, где они есть и в исходниках Linux, совпадают: `0x68`, `0x80`, `0x33`.
Два адреса из `msi-ec`, которые там названы реальными оборотами вентиляторов
(`0x71` и `0x89`), на этой прошивке читаются нулями даже при слышимом бусте,
поэтому не показываются: число, которое всегда ноль, хуже отсутствия числа.
`MSI_AP` — единственная часть карты, которая не сходится с именами полей,
поэтому её адреса под вопросом.

Всё это доступно **без `WinIo64.sys`** — того уязвимого ring-0 драйвера, что
приезжал с Dragon Gaming Center и который с машины удалён.

Две оговорки, выстраданные опытом. Сравнивать снимки можно **только
по `InstanceName`**, не по позиции в массиве: порядок перечисления не
гарантирован, и позиционный диff однажды выдал ложного кандидата, под который
чуть не записали мусор в EC. И значения большинства байтов меняются сами, так
что отличить флаг от датчика двумя снимками нельзя — нужен непрерывный опрос,
для него есть [poll-ec.ps1](tools/poll-ec.ps1).

## Что делает контроллер сам, а что оставлено софту

- **Cooler Boost** — вентилятор раскручивает сам EC, событие это лишь
  уведомление. Отдельного флага состояния обдува в железе нет: судить о нём
  можно только по значению вентилятора, и выключает его EC тоже сам.
- **Кнопка `0x220029`** — аппаратно не делает ничего. Чистый сигнал для софта,
  поэтому именно на неё удобно вешать своё действие.
- **Яркость и громкость** — прошивка и Windows справляются сами.
- **Fn+F2 (проецирование экрана)** — через ACPI-WMI не идёт вовсе. Событие не
  приходит даже при переданных кнопках и живой подписке: клавиша доставляется
  как обычный клавиатурный ввод, диалог открывает сама Windows. Переназначить её
  из этой программы нельзя.

## Сборка и запуск

```powershell
cargo build --release
.\target\release\msi-hotkeys.exe              # значок в области уведомлений
.\target\release\msi-hotkeys.exe --console    # то же в консоли, без значка
.\target\release\msi-hotkeys.exe --status     # только экран состояния
.\target\release\msi-hotkeys.exe --help
```

Режимы `--console`, `--status` и `--help` запускайте из терминала, уже открытого
от администратора. Повышение создаёт отдельный процесс, который не наследует
дескрипторы исходного терминала, поэтому его вывод в этот терминал не попадёт.

Релизный бинарь — 764 КБ, зависимости от `vcruntime140.dll` нет:
в [.cargo/config.toml](.cargo/config.toml) включена статическая CRT, так что
Visual C++ Redistributable на целевой машине не нужен. Полная сборка около
полутора минут, пересборка после правки — секунды.

```
rustup 1.29.1, rustc 1.99.0, stable-x86_64-pc-windows-msvc
wmi 0.18, serde, anyhow, chrono, tauri-winrt-notification, tray-icon, windows
```

Разработка:

```powershell
cargo test                    # 24 теста на чистых функциях, железо не нужно
cargo clippy --all-targets    # pedantic + nursery, предупреждений быть не должно
cargo fmt
.\tools\make-icon.ps1         # перерисовать иконку exe
```

| [buttons.rs](src/buttons.rs) | таблица кодов кнопок |
| [handler.rs](src/handler.rs) | подписка на события и реакция на нажатие |
| [readings.rs](src/readings.rs) | форматирование показаний — без WMI, поэтому тестируемо |
| [tray.rs](src/tray.rs) | значок, меню, поток опроса |
| [console.rs](src/console.rs) | экран `--status` |

Три потока, и не из вкусовщины: подписка блокируется, поэтому живёт отдельно;
показания нельзя снимать в потоке значка — трей инициализирует там COM как STA,
и созданное после этого соединение WMI открывается, но на все запросы отвечает
пустотой. Поэтому поток значка только качает очередь сообщений и копирует
готовые строки.

### Что он делает

- **В трее** — показания по строке на датчик, обновление раз в секунду,
  и «Выход», который возвращает кнопки прошивке.
- **`--status`** — экран, перерисовываемый раз в секунду: показания, кому
  принадлежат кнопки, версия прошивки EC, кривая вентилятора, все байты EC
  и последние нажатия. Только читает, поэтому может висеть рядом с работающим
  обработчиком.
- **Лог** — `%LOCALAPPDATA%\msi-hotkeys\events.log`, по две строки на нажатие:
  расшифрованное и сырой дамп всех окон EC.
- **Действия** — `%LOCALAPPDATA%\msi-hotkeys\actions.txt`, строка на кнопку:

  ```
  0x220029 = wt.exe
  ```

  Файл читается на каждом нажатии, так что правка срабатывает сразу.
  Команда идёт через `cmd`. Обработчик запущен с правами администратора,
  и запущенное им эти права наследует — об этом написано и в самом файле.

### Заметки по API, которые стоило бы знать заранее

- В `wmi` 0.18 `COMLibrary` больше нет, COM инициализируется внутри крейта,
  а `WMIConnection` сделан `!Send` — компилятор сам запрещает увезти соединение
  на другой поток.
- Пути с обратным слэшем писать сырой строкой: `r"root\WMI"`.
- `notification` блокирует поток до события, поэтому простой цикл `for`
  ничего не стоит в простое: ни опроса, ни таймера.
- Окна объявлены как `UInt8`, но батарея отдаёт слова, а ток — со знаком.
  Читатель, отбрасывающий отрицательные значения, сдвигает всё окно: так
  напряжение один раз прочиталось как температура.
- Тост без собственного AppUserModelID Windows молча выбрасывает, поэтому
  берётся чужой (PowerShell).
- Консоль не разбирает ANSI, пока не попросишь: нужен `SetConsoleMode`
  с `ENABLE_VIRTUAL_TERMINAL_PROCESSING`.

## Открытые вопросы

1. Автозапуск: задача планировщика при входе в систему, с повышением и скрыто.
2. Не определены коды `0x220023`, `0x220079`, `0x220279`, `0x22006F`.
3. Что означает средний байт кода: известно, что он изменчив и что пары кодов
   различаются его битом 1, но не известно, что именно он кодирует.
4. Единицы значения вентилятора и порядок индексов в окне `MSI_AP`.
5. Запись в кривую вентилятора не проверена — только чтение. Байты помечены
   `write=True`, так что управление оборотами, по-видимому, доступно.
6. Что назначить на кнопку `0x220029`. Пока она показывает тост с состоянием.
7. 17 байт EC остаются без расшифровки.

## Контекст: что уже сделано с машиной

- Dragon Gaming Center и Shortcut Manager удалены, служба `WINIO`
  и обе копии `WinIo64.sys` с диска уничтожены.
- Служба `Micro Star SCM` переведена в `Disabled`. `SCM.exe` остаётся
  в `HKLM\...\Run`, но без службы он бесполезен.
- Задачи MSI, Nahimic, NVIDIA backend и телеметрия совместимости отключены.
- Fast Startup выключен (`HiberbootEnabled = 0`) — выключение даёт настоящий
  холодный старт, драйверы выгружаются, EC сбрасывается.
- Драйверы обновлены: NVIDIA 582.78, Intel 31.0.101.2115.
